# 梅田 二館 座席表アーカイブ

T・ジョイ梅田と TOHOシネマズ梅田の上映スケジュールを追い、各回の座席の
埋まり具合を開映前に記録する。**ローカル実行版**。

GitHub Actions の `schedule` は指定どおりに発火しなかった（実測 14〜69 分
間隔、数時間空くこともある）。開映 30 分前・5 分前という細かい時刻を
当てにいく運転とは相性が悪いので、時計を握る役をこちら側に持ってきた。
`hub.py` が常駐して両方を叩く。

---

## ディレクトリ

```
cinema/
├── index.html              主入口。館を選ぶ + 売れ行きの折れ線
├── hub.py                  ローカルの時計。走査・撮影・集計を回す
├── data/
│   ├── stats.json          作品ごとの売れ行き（hub.py が生成）
│   └── hub_state.json      前回の走査日
│
├── tjoy/                   T・ジョイ梅田（旧 cinema リポジトリ）
│   ├── cinema.py
│   ├── index.html
│   ├── data/
│   │   ├── captures/YYYY-MM.json   記録の本体
│   │   ├── schedule.json           待ち行列
│   │   ├── films.json / index.json 派生物（作り直せる）
│   │   └── state.json
│   ├── media/{seats,posters,screens}/
│   └── logs/
│
└── toho/                   TOHOシネマズ梅田（旧 cinema-toho リポジトリ）
    ├── toho.py
    ├── index.html
    ├── data/
    │   ├── ...（tjoy と同じ）
    │   └── posters_shared.json     T・ジョイから借りるポスターの対応表
    ├── media/
    └── logs/
```

両スクリプトとも `ROOT = Path(__file__).resolve().parent` なので、
サブディレクトリに置くだけでデータの置き場所も一緒に付いてくる。
パスの書き換えは要らない。**データは統合しない**。索引もフロントも
館ごとに独立していて、主入口だけが両方を横断する。

## 動かす

```bash
python hub.py sweep      # まず 1 回、大範囲走査
python hub.py daemon     # 常駐。あとは放っておく
python hub.py serve      # 別窓で。http://localhost:8000/
```

常駐させたくないなら `tick` をタスクスケジューラ（または cron）から
**毎分**呼ぶ。状態は `schedule.json` の `slots` に入っているので、
落ちても飛ばしても次の tick が勝手に追いつく。

```
schtasks /create /tn cinema-tick /sc minute /mo 1 ^
  /tr "pythonw E:\Github\cinema\hub.py tick"
```

### そのほかのコマンド

| | |
|---|---|
| `python hub.py status` | 次に何がいつ起きるか |
| `python hub.py build` | 索引・ポスター貸出・統計を作り直す |
| `python hub.py sweep` | 大範囲走査を今すぐ |
| `python toho/toho.py doctor --deep` | 取得経路の自己診断。**まずこれ** |
| `python toho/toho.py inspect --live` | 構造が変わったときの調査用ダンプ |
| `python tjoy/cinema.py log -n 40` | ログの尻尾 |

> ブラウザから `fetch()` で JSON を読むので **`file://` では動かない**。
> `hub.py serve` か、任意の静的サーバ越しに開くこと。

## 1 日の流れ

```
09:30          大範囲走査（sweep）
               ├ 上映一覧を取り直す（今日から 2 日先まで）
               └ 全回の座席を 1 枚ずつ  ────────── slot 0（ベースライン）
各回の 30 分前  capture ──────────────────────── slot 1
各回の  5 分前  capture ──────────────────────── slot 2  ← 実態に一番近い
走査・撮影のあと  posters_shared.json と data/stats.json を作り直す
```

### 撮る時刻の決め方

`CAPTURE_PLAN = [30, 5]` が計画点。点を増やしたければ
`[45, 20, 5]` のように足す（降順で書くこと）。

```python
CAPTURE_PLAN = [30, 5]
PLAN_TOLERANCE_MIN = 2      # 起こされるのが多少早くても撮ってよい幅
SWEEP_DAYS = 2              # 大範囲走査で何日先まで見るか（今日 + N 日）
SWEEP_DAYS_NIGHT = 1        # 深夜〜早朝はここまで
NIGHT_HOURS = (1, 7)        # 「深夜〜早朝」の範囲（JST の時、終端は含まない）
KEEP_SLOT_SHOTS = False     # True にすると計画点ごとに画像を残す（3 倍になる）
```

### 走査の射程は時刻で変わる

01:00〜07:00 に回したときは **今日と翌日**、それ以外の時刻なら **今日と翌々日**
まで見る。深夜〜早朝は先の日付がまだ売っていないことが多く、選座画面に
入れないので、舐めても空振りが増えるだけになる。射程を 1 日縮めたほうが、
同じ時間で今日と明日を丁寧に撮れる。

起動が遅れて 30 分前と 5 分前をまたいでしまったときは、**深いほう**
（開映に近いほう）だけを撮り、跨いだ点はまとめて済みにする。あとから
30 分前の図を撮り直しても実態には近づかないため。

消化済みの点は `schedule.json` の各回の `slots` に残る。
`[0, 1, 2]` まで揃うと確定として行列から外れる。

### 3 点ぶんの数値はどこに残るか

記録は `id`（劇場-日付-時刻-スクリーン-作品）で一意なので、同じ回を 3 回
撮っても勝ち残る記録は 1 件だけ（開映に一番近い読み）。それだけだと
売れ方の推移が消えるので、数値の点を記録の `history` に畳んで持たせる。

```json
"history": [
  {"slot": 0, "lead": 540.0, "sold":  38, "vacant": 338, "occupancy": 0.1011},
  {"slot": 1, "lead":  30.0, "sold":  91, "vacant": 285, "occupancy": 0.2420},
  {"slot": 2, "lead":   5.0, "sold": 114, "vacant": 262, "occupancy": 0.3032}
]
```

`history` の合流は点の和集合で、同じ点が二重に来たら開映に近い読みを残す。
可換かつ冪等なので、ローカルとクラウドがどちらの順で合流しても、二度
流しても同じ結果になる（captures / media の規則と同じ性質）。

画像は既定では 1 回につき 1 枚を上書きする。3 枚とも残したいなら
`KEEP_SLOT_SHOTS = True`。TOHO は 1 日 44 回あるので、3 日ぶん × 3 点で
1 日 8MB 前後になる。数値だけなら `history` に全点入っている。

## 壊れた読みで良い記録を上書きしない

同じ回の記録は id が同じなので 1 件しか残らず、順位は長らく「開映に近いほうが
勝つ」だけで決めていた。ところが座席ページには入れたのに座席表が描かれない、
途中までしか描かれない、という失敗の仕方がある。そのまま順位を付けると、
開映 5 分前に取れた **0 席の読み** が 30 分前の正しい読みを追い出してしまう。

そこで順位の第 1 要素を「質」にした。

| 質 | 中身 |
|---|---|
| 2 | 座席が読めていて、公称席数とも一致する |
| 1 | 座席が 0 件、または公称席数と 3 席以上ずれている |
| 0 | 予定だけの記録（座席未取得） |

質が下の記録は、どれだけ開映に近くても上を押しのけられない。公称席数が
分からないスクリーンのために、既存の記録そのものを物差しにする検査
（`looks_truncated`）も併せて置いてある。同じ回で箱が 1 割も縮むのは
読み切れていないときだけで、正常な変化ではない。検査は両向きに効くので、
壊れた読みが先に入っていた場合はあとから来た正しい読みが取り返す。

**満席は壊れた読みではない。** `sold=376 / vacant=0 / total=376` は公称席数と
一致するので質 2 と判定され、通常どおり更新される。**時間切れやページに
入れなかった場合は、そもそも記録が作られない**（`no-page` としてログに残るだけ）
ので、既存のデータには一切触れない。

推移の `history` にも同じ物差しが効く。読み切れていない点は落とす。折れ線が
谷になるだけで「その時刻にそれだけしか売れていなかった」ではないため。
一度取り込んでしまった点にも遡って効く。

順序を入れ替えた 720 通りで結果が一致することを確認済み。合流の可換性・
冪等性はこの変更のあとも保たれている。

## ポスターの貸し借り

TOHO の座席ページには作品画像が出ないことが多い。同じ作品を撮っている
T・ジョイ側には画像があるので、それを借りる。

`film_key` では突き合わせられない。TOHO は「Ｍｉｃｈａｅｌ／マイケル」と
全角で、T・ジョイは半角で書くので、同じ作品でも別の鍵になる。そこで
題名を正規化（全角→半角、記号と空白を落とす）した文字列で照合し、
結果を `toho/data/posters_shared.json` に置く。`toho.py` の索引作りが
それを拾って埋める。借り物には `poster_from: "tjoy"` が立つ。
見つからなければ**空欄のまま**。

## 売れ行きの図（data/stats.json）

主入口の折れ線。作品ごとに 1 枚、線は劇場ごとに 1 本。
**累計**と**日別**を切り替えられる。

```json
{
  "films": [{
    "title": "...", "poster": "tjoy/media/posters/....jpg",
    "totals": {"tjoy": {"sold": 5070, "shows": 30, "seats": 9930},
               "toho": {"sold": 5068, "shows": 30, "seats": 9930}},
    "series": {"tjoy": {"2026-08-20": 482, "2026-08-21": 372},
               "toho": {"2026-08-20": 608, "2026-08-21": 361}}
  }]
}
```

1 回あたりの席数は記録本体と `history` の**最大値**を採る（合流の順によっては
history のほうが深い点を持っていることがあるため）。

### 作品の突き合わせ

`film_key` では突き合わせられない。全角・半角の違いに加えて、T・ジョイは
「国宝 Kokuhou」のように邦題のうしろへローマ字を足すが、TOHO は足さない。
そのままだと同じ作品が 2 本に割れて、折れ線が片側しか描けない。

`hub.py` の `norm_title` が照合用の鍵を作る。全角を畳んで記号と空白を落とし、
さらに **日本語で終わる題の末尾に付いたラテン文字** だけを削る。削るのは
次をすべて満たすときに限る。

- 題に日本語（漢字・かな）が含まれている
- その最後の日本語文字より後ろが英数字だけで出来ている
- その長さが 3 文字以上

| 例 | 鍵 | |
|---|---|---|
| `国宝 Kokuhou` / `国宝` | `国宝` | 合流する |
| `ふれる。 Fureru` / `ふれる。` | `ふれる` | 合流する |
| `８番出口 The Exit 8` / `8番出口` | `8番出口` | 合流する |
| `劇場版 Fate/stay night 桜の章` | 全部残る | 途中のラテン文字は削らない |
| `ONE PIECE FILM RED` | 全部残る | 日本語が無いので削らない |
| `エヴァンゲリオン:Q` | 全部残る | 尾が 3 文字未満 |
| `国宝` / `国宝の秘密` | 別の鍵 | 誤って合流しない |

**表示に使う題名はどちらの館も元のまま。** ここで作るのは照合用の鍵だけで、
各館のページの見え方には一切影響しない。

> **これは興行収入ではない。** 開映直前の座席表を数えているだけなので、
> 直前・当日券の一部は入らないし、券種も区別しない。座席表が撮れなかった
> 回は数に入らない。**実数の下限**として読むこと。

## 知っておくとよいこと

**TOHO は 3 日先までしか売っていない。** 実測では今日を含む 3 日が販売中で、
4 日目以降は全 44 件が「販売期間外」だった。`SWEEP_DAYS = 2`（今日 + 2 日）
はその境目に合わせてある。販売前の回は選座画面に入れないので走査は
それを飛ばし、開売後の次の走査でベースラインを拾う。サイト側の挙動で、
こちらの不具合ではない。

**大範囲走査は軽くない。** TOHO は 1 回撮るのに「一覧 → 日付タブ → 上映回 →
中間ページ → 座席表」の 5 手が要る。44 回 × 3 日 に礼儀の待ち時間を足すと
1 巡 15〜25 分。重ければ `toho.py` の `CAPTURE_ONLY` で絞れる。

```python
CAPTURE_ONLY = {
    "screens": ["01", "02", "03"],   # 大きい箱だけ
    "min_seats": 400,                # これ未満は撮らない
    "max_per_round": 8,              # 開映の早い順に N 件
}
```

**別館は休館中。** TOHO のスクリーン 9・10 は耐震性確認のため休館。
`CINEMAS[0]["venues"]` で `active: false` にしてあるので行列に積まれない。
再開したら `true` に戻すだけ。

**相手サイトへの配慮はそのまま。** リクエスト間 3 秒 + 揺らぎ、robots.txt の
確認、403/429/5xx を踏んだら 180 分の全面停止。ローカルにしても緩めていない。

**git 同期は残してある。** `pull` / `push` はそのまま使える（データブランチは
`cinema-data` / `toho-data`）。ローカル運転では使わなくてよいが、記録の
合流規則は可換・冪等なので、両方から走らせても壊れない。

## 常駐させる

```
python hub.py daemon
```

これだけでよい。30 秒ごとに自分で時計を見て、走査と撮影を回す。
tick 中に例外が出ても止まらず、次の周回で立て直す。

ただし Windows では、コンソールを閉じたりサインアウトしたりすると
道連れで死ぬ。落ちたら誰も気付かないまま何日も空くので、**タスク
スケジューラに任せるほうを勧める**。

### 方法 A（推奨）— tick を毎分呼ぶ

常駐プロセスを持たない。落ちる先が無いので、いちばん堅い。

```
schtasks /create /tn cinema-tick /sc minute /mo 1 ^
  /tr "pythonw E:\Github\cinema\hub.py tick" /rl highest
```

判断材料はすべて `schedule.json` の `slots` に入っているので、
何回か飛ばされても次の tick が勝手に追いつく。走査中（15〜25 分）は
次の tick が重なるが、`hub.py` は劇場スクリプトを順に呼ぶだけなので
実害は無い（気になるなら `/mo 2` にする）。

### 方法 B — daemon をログオン時に起こす

```
schtasks /create /tn cinema-daemon /sc onlogon ^
  /tr "pythonw E:\Github\cinema\hub.py daemon" /rl highest
```

タスクのプロパティで「タスクが失敗した場合の再起動間隔: 1 分」を
入れておくこと。これが無いと A の堅さに届かない。

### どちらでも

- PC がスリープすると当然止まる。撮り逃した回は次の走査で
  ベースラインだけ拾い直す（30 分前・5 分前は取り返せない）。
  電源設定でスリープを切っておくと取りこぼしが減る。
- 動いているかは `python hub.py status` と `logs/*.log` で見る。
- 閲覧用の `hub.py serve` は別プロセス。見るときだけ立ち上げればよい。
